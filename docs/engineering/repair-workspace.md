# Repair writes and candidate identity

A recorded `owned` cohort describes physical quiescence, not write permission.
After that reconciliation, an investigator uses `engineering admin workspace-write
--reason <reason>` through its private invocation socket. A successful host receipt
authorizes that bound investigator to repair the returned registered project root.
It does not authorize another invocation, an original execution worktree at a
different path, a runtime/service update or business completion.

## Host authorization

The host rechecks the actual investigator PID, group and birth marker, native
source, project fence and owned writer inventory. It reads actual registered-root
content and rechecks the same native cohort after the read before saving a grant.
The command cannot supply a directory, content version, native scope or process
identity. Missing, draining or changed ownership cannot return authorization.

The immutable grant binds the Case, attempt, generation, session, supervision and
intent revision; actual investigator identity; original source inspection and
observation IDs; registered root; writer-inventory hash; and initial content
version. Repeating the same grant preserves its original baseline after edits.
Changed reasons, source/cohort or original observations need a new repair attempt.

The trusted local investigator makes the source edits with its existing tracked
provider group. Preserve unrelated user changes and all frozen original contracts.
This is a protocol authorization boundary, not an OS sandbox against a hostile
same-user process. It neither copies a workspace nor creates a separate patch
worker, build environment or runtime artifact.

## Candidate capture and independent verification

After edits, `engineering admin workspace-candidate --key <stable-key>` makes the
host repeat actual process/source/content checks. It saves an immutable candidate
receipt bound to the write grant and the freshly observed content version. The
host also creates `native-candidate/<key>` change evidence containing both
receipts. Agent evidence commands cannot use that reserved namespace.

Keys use 1–80 ASCII letters, digits, dots, colons, underscores or hyphens. An exact
retry is idempotent; the same key cannot replace an earlier content version.
Another candidate requires another key. Each attempt retains at most 100 candidates.
Status exposes the grant and retained candidates; history retains their native
change evidence. A candidate records content identity, not a frozen copy of every
source file or proof of a running service's version.

A `verification-requested` submission must include the candidate's exact version,
its reserved evidence key and every original observation ID. A manually written
change fact or cached owned progress cannot replace a native candidate. Host input
preparation freshly rechecks content and records the exact candidate hash in the
independent input envelope. Read validation checks the retained candidate and
grant identities. The independent Test still derives all targets from original
contracts and failures, without inheriting repairer-proposed checks.

The existing [independent verification](repair-verification.md) then waits for the
repair group's physical exit, allocates separate Test and native-check generations,
and checks the exact candidate version before/after actual commands. Stop or
source changes refuse further grants/capture/submission. These gates do not claim
immediate OS revocation of an earlier grant on every business UI change. Verified
repair alone still holds the business fence. The separate [verified handoff](repair-handoff.md)
now connects controlled publication, authenticated resume and ordinary-result
observation before guarded Case closure.

## Storage and evidence

Schema 8 adds `admin_repair_write` and `admin_repair_candidate`. Upgrades retain
original observations, old inputs and process barriers. Settled waiting/prepared
or verified Cases without a live allocation return to repair because their older
inputs did not require native write/candidate receipts. Unknown active launches
still require physical reconciliation; migration does not invent exit evidence.

Controlled tests run a test-created SDK provider that obtains authorization,
changes a real temporary Git repository and captures a candidate through the
private socket, then run separate original-contract verification. A PostgreSQL
and bundled-worker test uses a real recorded investigator group, rejects a
draining project, authorizes writes after cleanup, captures actual content and
keeps business blocked through physical handoff. Kernel tests cover immutable
baselines/keys, reserved evidence, changed scope/originals, stopped intent, damaged
receipts and schema upgrades. This does not establish real-model, packaged or
Linux runtime acceptance.
